# Official OBD → GrowthEvo Locked OPE

GrowthEvo itself requires Python 3.11+, while the official Open Bandit Pipeline release metadata is tied to an older Python/scientific stack. The benchmark bridge is therefore intentionally **process-isolated** rather than added as a runtime dependency of GrowthEvo.

The workflow has two environments:

1. an official OBP-compatible environment exports OBD evidence into GrowthEvo's JSONL contract;
2. the normal GrowthEvo Python 3.11+ environment performs estimator selection and the locked final evaluation.

This avoids changing the causal/OPE implementation merely to satisfy a legacy dependency stack.

## Why Open Bandit Dataset

Open Bandit Dataset contains logs generated by multiple production policies on the same ZOZOTOWN platform. The official OPE evaluation protocol uses one policy's log as off-policy evaluation evidence and another policy's factual rewards as an on-policy reference. This makes OBD unusually suitable for evaluating estimation error rather than only reporting an unverified OPE point estimate.

The exporter currently implements the canonical `random → BernoulliTS` direction from the official quickstart.

## Environment A: official OBP exporter

Create an environment compatible with the official OBP release/source, then run the standalone exporter from this repository:

```bash
python scripts/export_obd_locked_ope.py \
  --campaign all \
  --output-dir /tmp/growthevo-obd-all \
  --validation-fraction 0.5 \
  --n-sim 100000 \
  --q-folds 3 \
  --q-model logistic \
  --random-state 12345
```

If the full OBD has been downloaded manually, provide its root with:

```bash
--data-path /path/to/open_bandit_dataset
```

When no path is given, behavior follows the installed official `OpenBanditDataset` implementation (which historically exposes the small example dataset for quickstart use).

### Outputs

The exporter writes:

- `validation.jsonl`
- `holdout.jsonl`
- `ope_candidates.json`
- `export_manifest.json`

The JSONL files conform exactly to `growthevo-locked-ope`.

## Target-policy probability

The exporter reconstructs the production BernoulliTS policy using the official interface and Monte Carlo action distribution:

```text
BernoulliTS(
    is_zozotown_prior=True,
    campaign=<campaign>
).compute_batch_action_dist(...)
```

For each factual row `i`, action `a_i` and position `p_i`, GrowthEvo receives:

```math
\pi_e(a_i\mid x_i,p_i)
=
\mathrm{action\_dist}[i,a_i,p_i].
```

The exporter verifies that target-policy probability mass sums to one for each exported row/position.

## Q terms for DM / DR / DR-OS

With `--q-model logistic` (default), each chronological evidence window independently calls the official `RegressionModel.fit_predict(..., n_folds=K)` protocol. Thus validation Q predictions do not learn from holdout rewards, and holdout Q predictions do not learn from validation rewards.

For the factual action:

```math
\widehat q_i
=
\widehat Q_i(a_i,p_i).
```

For the target-policy expected reward term:

```math
\widehat q_{\pi,i}
=
\sum_a
\pi_e(a\mid x_i,p_i)\widehat Q_i(a,p_i).
```

These become GrowthEvo's `baseline_q` and `target_q` respectively.

`--q-model zero` exists only for IPS/SNIPS/β*-IPS debugging when an OBP reward model cannot be fit. A zero-Q export must not be used to claim DM/DR performance.

## Paired chronological validation and holdout

GrowthEvo needs a validation cohort for estimator/hyperparameter selection **before** final holdout evaluation. The exporter therefore creates two non-overlapping chronological windows for both production policies:

- earlier random-policy rows → validation OPE evidence;
- earlier BTS factual rows → validation on-policy reference;
- later random-policy rows → final holdout OPE evidence;
- later BTS factual rows → final holdout on-policy reference.

The split fraction is fixed by `--validation-fraction` before estimator selection.

This is a GrowthEvo locked-selection extension of the official two-policy OPE idea. It should not be mislabeled as the exact original OBP benchmark protocol; `export_manifest.json` records the paired-window definition explicitly.

## Stable row identity

Each random-policy row receives an identity containing:

- behavior policy;
- campaign;
- raw CSV index;
- timestamp;
- factual item;
- factual position;
- sorted-data ordinal.

The locked runner rejects validation/holdout identity overlap.

The exporter does **not** invent a default cluster ID. A cluster-robust standard error should only be requested after the experiment defines a defensible cluster/block unit.

## Environment B: GrowthEvo 3.11+

After export, enter the normal GrowthEvo environment and run:

```bash
growthevo-locked-ope \
  --tuning-jsonl /tmp/growthevo-obd-all/validation.jsonl \
  --test-jsonl /tmp/growthevo-obd-all/holdout.jsonl \
  --candidates-json /tmp/growthevo-obd-all/ope_candidates.json \
  --tuning-reference <validation_reference_from_manifest> \
  --test-reference <holdout_reference_from_manifest> \
  --benchmark open-bandit-ope \
  --dataset obd-all-random-to-bts \
  --commit-sha "$(git rev-parse HEAD)" \
  --output benchmark-result.json
```

Only the estimator/hyperparameter configuration selected on the validation reference reaches the final holdout reference.

## Default candidate grid

The exporter emits a finite, predeclared grid containing:

- cross-fitted β*-IPS;
- Doubly Robust;
- IPS;
- SNIPS;
- two SWITCH-DR thresholds;
- two DR-OS shrinkage values;
- Meta-OPE/BLUE diagnostic.

The grid is intentionally small. Expanding a hyperparameter grid after inspecting validation or holdout results is another form of adaptive selection and must be documented as a new protocol.

## Full-data promotion

The 10,000-row-per-policy example OBD is useful for pipeline verification, but it is not a replacement for a full-data benchmark claim. README performance promotion should use the full research release where practical and must commit or archive:

- `export_manifest.json`;
- the exact candidate JSON;
- validation scoreboard;
- locked holdout artifact;
- code commit SHA;
- dataset release/source identity.
